# 計画書: rig-service — 3Dモデル自動リグ+VRM化サービス

> 状態: **Phase R1〜R4 完了**(2026-07-25)。R3-3 の VRMA / BVH 読み込みのみ未実装。
> 実装は本リポジトリ、使い方は [`../README.md`](../README.md) を参照。
> **image-3d とは別リポジトリ**(計画書 §1「独立したサービス」の通り)。
> 本ドキュメントは image-3d で生成した3Dポリゴンモデルに
> ボーン(リグ)を付与し、VRMモデルのようにポーズデータで動かす/Godot等の
> ゲームエンジンで使うための検討結果と実装計画をまとめたもの。
> 新しいチャットセッションで再開する場合は本ドキュメントを起点にする。

## 1. ゴール(確定済み要件)

image-3d で画像から生成した3Dキャラクターモデルを、
**VRMモデルのようにポーズデータで動かせる**ようにする。

| 項目 | 決定内容 |
|---|---|
| 入力ポーズ | **Tポーズ前提**。ユーザーがTポーズの立ち絵を用意する(UI上で推奨を明示)。ポーズ推定・正規化フェーズは不要 |
| 駆動方式 | **ポーズデータ**(ポーズJSON / VRMA / BVH)。**text-to-motion(自然言語駆動)は保留**(将来拡張) |
| プロジェクト形態 | **image-3d とは独立したサービス(rig-service)**。image-3d は生成済みGLBを持ってURL(REST API)を呼ぶだけの疎結合 |
| リグエンジン | **bpy(Blender 4.2 LTS)を第一実装**。pip の `bpy` モジュール(専用 Python 3.11 venv)を優先し、システムBlenderサブプロセスをフォールバックとする(§4参照) |
| VRMバージョン | **VRM 1.0**(godot-vrm / three-vrm / UniVRM が対応)。ただし最小マイルストーンは「リグ済みGLB」(Godot 4 ネイティブインポート)とし、VRM化は付加ステージ |
| ターゲット環境 | **Godot**(godot-vrm アドオン or ネイティブglTF+BoneMapリターゲット) |
| アニメーション | 同梱 .vrma クリップ(idle/walk/wave/bow 等)で即再生可能にする |

## 2. 背景: image-3d の現状(調査結果)

- 生成物は**静的な単一メッシュ**(`trimesh.Trimesh`)。`server/jobs.py` の
  `_export_all()` が stl/3mf/obj/glb を出力するが、ボーン/スキン/アニメーション情報なし。
- ジェネレータはプラガブル(mock / hunyuan3d / pixal3d)。Pixal3D は
  **別venv(`.venv-pixal3d`)+外部プロセス**で統合済み → rig-service も同パターンが使える。
- 受け渡しは GLB(glTF 2.0)。glTF はスキン+アニメーションを正式サポート。
- ビューア(`web/viewer.js`)は GLTFLoader 使用済みだが `AnimationMixer` は未使用。
- Hunyuan3D 等は**入力画像のポーズのまま**メッシュを出力する
  → Tポーズ入力ならリグの自動ウェイトが安定する(Tポーズ前提の根拠)。

## 3. なぜ VRM 準拠を核にするか

| 要求 | VRM化で得られるもの |
|---|---|
| ポーズデータで動かす | VRMは**ヒューマノイドボーン名が標準化**(hips/spine/chest/head/leftUpperArm…)。ポーズ=各ボーンの回転の辞書として機械的に適用できる。標準アニメ形式 **.vrma (VRM Animation)** も存在 |
| 自然言語で動かす(将来) | text-to-motionモデルの出力(SMPL骨格)を標準ボーンへリターゲットすれば任意のVRMに適用できる |
| ゲームエンジンで使う | Unity(UniVRM)/ Unreal(VRM4U)/ **Godot(godot-vrm)** / Web(three-vrm)がそのまま読める |

**「生成メッシュ → VRM humanoid準拠のリグ済み .vrm」が成立すれば、
動かす側(ポーズ/エンジン)は既存エコシステムに乗れる**。これが最重要マイルストーン。

### Godot での扱い(VRM 0.x / 1.0 の結論)

| 出力 | Godotでの扱い | 必要なもの |
|---|---|---|
| リグ済みGLB(スキン付きglTF) | Godot 4 は**ネイティブでインポート可能**。ボーン名が標準的なら `SkeletonProfileHumanoid` + BoneMap でリターゲット可能 | VRM仕様は不要 |
| VRM 1.0 | [godot-vrm](https://github.com/V-Sekai/godot-vrm) アドオンで 0.x/1.0 両対応。humanoidボーンマップ・スプリングボーン・表情が自動設定される | VRMエクスポータ必須 |

→ 推奨は **VRM 1.0**。ただし最小E2Eは「リグ済みGLB → Godotネイティブインポート」で先に通す。

## 4. リグエンジンの比較検討(Blender以外も含む)

| 方式 | 仕組み | 長所 | 短所 | 判定 |
|---|---|---|---|---|
| **A. Blender 4.2 LTS ヘッドレス**(`blender --background --python` + VRM Add-on) | アーマチュア配置→ボーンヒート自動ウェイト→VRMエクスポート | 自動ウェイト品質が高い(bone heat)・VRM出力が既製アドオンで完結・無償 | 外部バイナリ依存(~300MB)・起動オーバーヘッド数秒 | **フォールバック** |
| **B. bpy pipモジュール**(`pip install bpy==4.2.*`) | Aと同じBlender機能をPythonモジュールとして利用 | サブプロセス不要・venv完結 | Python 3.11 固定(image-3d は 3.12)→ **独立サービスなら専用venv 3.11 で解決** | **第一実装** |
| C. ピュアPython自作(pygltflib + 距離ベースウェイト) | glTF skin/joints/weights を numpy で直接構築 | 依存最小 | ボーンヒート級のウェイト品質の自作は高コスト。関節付近が破綻しやすい。VRM拡張JSONも自作 | 不採用 |
| D. UniRig(VAST-AI-Research、学習モデル) | GPUでスケルトン+スキンウェイトを推論 | 変則形状にも強い | GPU占有・依存重・結局VRM化にBlender等が要る | 将来オプション |
| E. クラウドAPI(Tripo/Meshy auto-rig) | SaaS | 実装最小 | ローカル完結の前提に反する・有料 | 不採用 |

**結論**: B(bpyモジュール、専用 Python 3.11 venv)を第一実装、
A(システムBlender 4.2 LTS サブプロセス)をフォールバック。
**両者は同じ bpy スクリプトを共有**でき、将来 D への差し替えもプラガブルにする
(image-3d の Generator 抽象と同じ設計思想)。

### VRM出力

- **[VRM Add-on for Blender](https://vrm-addon-for-blender.info)(saturday06版、MIT)** を使用。
  ヘッドレス実行・Pythonからの操作に対応、CI自動化実績あり。
- humanoidボーンマッピング(hips/spine/head/arms/legs…)をスクリプトで自動設定し
  VRM 1.0 をエクスポートする。

### Tポーズ前提による単純化

関節位置推定は学習モデル不要で決定的に配置可能:
- バウンディングボックス比率(人体プロポーション: 頭=上端~85%、腰=~50% 等)
- 左右対称性
- 水平に伸びた腕の検出(Tポーズなので腕はX軸方向に伸びる)

で 15〜20 ボーンのヒューマノイドアーマチュアを配置し、
Blender の `parent_set(type='ARMATURE_AUTO')`(ボーンヒート自動ウェイト)でスキニングする。

## 6. API仕様(案)

ベースURL: `http://127.0.0.1:8100`

| メソッド | パス | 説明 |
|---|---|---|
| POST | `/api/rig` | multipart: `model`(GLB必須)+ `params` JSON(`vrm: bool`, `height_m: float`, `bone_set: "standard"`)→ `{job_id}` |
| GET | `/api/rig/jobs/{id}` | 状態(queued/rigging/exporting/completed/failed)+ボーン数・ウェイト統計・警告 |
| GET | `/api/rig/jobs/{id}/download?format=glb\|vrm` | リグ済みGLB / VRM 1.0 |
| POST | `/api/rig/jobs/{id}/pose` | ポーズJSON(`{boneName: quaternion}`)/ VRMA / BVH → プレビュー反映・ポーズ済みGLB取得 |
| GET | `/api/motions` | 同梱クリップ一覧 |
| GET | `/api/health` | エンジン可否(bpy/blender/vrm-addonバージョン) |
| GET | `/` | three-vrm プレビューUI |

### image-3d 側の改修(最小)

- 設定 `IMAGE3D_RIGSVC_URL` を追加(未設定ならボタン非表示)。
- 完了ジョブに「リグ/VRM化」ボタン → `model.glb` を rig-service にPOSTし、
  返ってきたジョブのプレビューURLを新タブで開く。

## 8. リスクと対策

| リスク | 対策 |
|---|---|
| `bpy` pipパッケージがPython 3.11固定 | 独立サービスなので専用venvで解決。ダメならBlender CLI方式(同一スクリプト共用)へ自動フォールバック |
| VRM Add-onのヘッドレス動作不成立 | R2冒頭で技術スパイク。不成立でもR1のリグ済みGLB+Godot BoneMapで実用は確保済み(段階的マイルストーンの意義) |
| 自動ウェイトの品質(スカート・髪・付属物) | まず素体で検証。破綻部位はウェイト統計で警告として返し、Blenderでの手修正を案内 |
| GPL(Blender/bpy) | 独立プロセス/独立サービスなので image-3d 本体へのライセンス波及なし。rig-service 自体の配布形態のみ注意 |
| メッシュ品質(非多様体・高ポリ) | image-3d の後処理済みメッシュ(`max_faces` 簡略化済み)を入力とする |

### ⚠ 重要な発見1: image-3d の GLB は **Z-up**(glTF仕様違反)

`data/jobs/*/model.glb` の生JSONを直接確認した結果:

- `POSITION` の `min=[-34.91, -21.69, 0.0] / max=[34.91, 21.70, 100.0]` → **Z が上方向**
- ノードは `world`(変換なし)→ `geometry_0` のみで、**Y-up への補正回転が無い**
- glTF 2.0 仕様は **Y-up が必須**。つまり trimesh 出力は仕様非準拠

image-3d 側はこれを**承知の上でビューア側で補正**している
(`web/viewer.js:114-118`「生成メッシュ(Z-up, 床=z0)をX軸-90度回転して」)。

そのため Blender にインポートすると(Y-up→Z-up 変換が入り)モデルは
**Y軸方向 -100〜0 に横倒し+反転**した状態になる。

**rig-service での対処(R1-2 の設計に反映する)**:

1. インポート直後に**実測バウンディングボックスの最長軸から上方向を判定**して正規化する
   (スパイクではこの方式で自動ウェイトまで正常動作を確認済み)。
2. **出力は glTF 仕様準拠の Y-up・原点=足元**に正規化する。Godot / VRM / three-vrm は
   いずれも仕様準拠を前提とするため、image-3d の Z-up 慣習を引き継いではいけない。
   rig-service は自前の three-vrm プレビューUIを持つので image-3d のビューアとは衝突しない。
3. スケールも同時に正規化: 入力は**高さ100単位**(造形用)。VRM/Godot はメートル系なので
   `height_m`(既定 1.6)に合わせて **× height_m/100** する。

### ⚠ 重要な発見2: glTF インポータが `Icosphere` を作る

アーマチュア入りGLBを再インポートすると、ボーン表示用 custom shape として
`Icosphere` メッシュオブジェクトが生成される。`glTF_not_exported` コレクションに
入るためエクスポートには含まれないが、**シーン内のメッシュを数える処理では除外が必要**
(`o.users_collection` に `glTF_not_exported` が無いことを確認する)。

## 11. R1-2 / R1-3 実装結果(2026-07-25)

実装は `rig-service/`。テストは `.venv-rig/bin/python -m pytest tests/ -q` で 40件全通過。

### 計画からの変更点

| 項目 | 計画 | 実装 | 理由 |
|---|---|---|---|
| bpyエンジンの呼び出し方 | bpyモジュールを**プロセス内**で直接呼ぶ | **同一venvのPythonでサブプロセス実行** | bpyはグローバル状態を持つシングルトンでスレッドセーフでない。FastAPIのワーカースレッドから `bpy.ops` を叩くのは非サポートで、失敗時にサーバごと落ちる(実際 Workbench レンダリングは GL コンテキスト不在で**捕捉不能な abort** を起こす)。サブプロセスならジョブ単位でメモリも解放され、CLI方式とスクリプトを完全共有できる。追加コストは bpy の import 1〜2秒のみ |

### 座標系の正規化(計画書 §10 発見1 への対処)

`server/bpy_scripts/proportions.py` に bpy 非依存で実装(単体テスト可能)。

- **上方向軸の判定**: 「最長軸=上」は使えない。Tポーズでは指先間の幅が身長に匹敵し
  左右軸と拮抗するため。glTFインポータの Y-up→Z-up 変換で**左右軸は常に Blender X**
  になることを利用し、**Y と Z の広がりの比較だけ**で「元がY-upかZ-upか」を判定する。
- **正面方向の判定**: 2つの独立な手がかり(足はつま先方向へ突き出す / 後頭部・髪は
  背面側に膨らむ)を突き合わせ、不一致なら警告を出す。image-3d の既存生成物 12 体で
  両者は一致し、**いずれも正面 = -Y**(Z-up 原座標系)だった。
- 出力は **Y-up・原点=足元・メートル系・キャラは +Z を向く**(VRM 1.0 の要求と一致)。

### Tポーズ判定と関節位置の実測

腕が水平に張り出したスラブ帯を探し、その中心を肩の高さとする。
スカート等の**縦に長い幅広部**と区別する決め手は「**帯が高さ方向に薄い**」こと
(腕を下ろしたキャラでは幅広部が全高の 0.8 に及ぶのに対し、腕は 0.22 以下)。

股下は左右方向のヒストグラムで**中央をまたぐ空ビンの幅**から検出する。
「中心付近に頂点が無い」を絶対距離で判定すると脚を閉じたキャラで破綻するため。

実測した肩・股下・首・脚幅・腕長は妥当範囲でのみ採用し、範囲外なら人体標準比へ
倒して `warnings` に明示する。**妥当範囲は人体標準よりかなり広い**
(肩 0.40〜0.92 / 股下 0.10〜0.65 など)。実運用の入力がぬいぐるみ・動物型の
デフォルメ体型(肩が全高の 49%、股下が 16%)で、人体標準比に丸めると
関節位置が丸ごとズレるため。

## 13. R2 VRM 1.0 出力の実装結果(2026-07-25)

### 計画からの変更: VRM Add-on を使わず自前実装にした

| | 計画 | 実装 |
|---|---|---|
| 方式 | VRM Add-on for Blender(saturday06版)をヘッドレス組込み | **`server/vrm.py` で `VRMC_vrm` 拡張を自前生成** |

**VRM 1.0 は glTF 2.0 + `VRMC_vrm` 拡張にすぎない**。R1-4 で確認した通り
rig-service の出力GLBは既に VRM humanoid の要求(Y-up・原点=足元・メートル系・
アバターは +Z を向く・標準ボーン名)をすべて満たしていたため、
**JSONチャンクに `meta` と `humanoid.humanBones` を足すだけ**で VRM になった。

自前実装にした理由:

- ダウンロードした第三者コードをサービスのプロセス内で実行せずに済む
- bpy 非依存なので**単体テストが速く**(21件が0.1秒)、リグ処理と分離できる
- 計画書 §8 のリスク「VRM Add-onのヘッドレス動作不成立」が**消える**
- アドオンのバージョン差によるAPI変化に追随しなくてよい

代わりに MToon マテリアル・表情(expressions)・スプリングボーンは扱わない。
いずれも現状スコープ外で、必要になれば `VRMC_springBone` 等を同じ方式で足せる。

### 実装

- `server/vrm.py` — GLB の読み書き / `VRMC_vrm` 生成 / 仕様検証(**純Python・依存ゼロ**)
- ボーン名の対応は R1-2 の21ボーン → VRM の lowerCamelCase 名を引くだけ
- VRM化はリグ後の独立ステージ(`jobs.py`)。**失敗してもジョブは failed にしない**
  (リグ済みGLBは Godot で使えるため、警告を残して VRM だけ諦める)
- `params.vrm_meta` でタイトル・作者・ライセンス・利用許諾を指定できる。
  **既定は最も制限的**(作者のみ・非営利・改変再配布不可)。生成物の権利者が
  誰かはサービス側で判断できないため、緩めるのは呼び出し側の明示指定に限る

### 検証結果

`validate()` が VRM 1.0 の必須条件を機械的に検査する:

| 検査 | 内容 |
|---|---|
| 拡張 | `extensionsUsed` に `VRMC_vrm`、`specVersion == "1.0"` |
| メタ | `name` / `authors` / `licenseUrl` が非空 |
| humanBones | 必須15ボーンの存在、ノード参照の範囲 |
| 階層 | hips 以外のすべてが **hips の子孫**であること |
| 向き | head が hips より上 / leftHand が rightHand より +X / **つま先が足首より +Z** |

実生成メッシュ(Tポーズぬいぐるみキャラ)で **humanoid 21ボーン・検証エラーゼロ**。
さらに **VRM を Godot のネイティブ glTF インポータでも読めること**を確認した
(`extensionsRequired` に入れていないため、VRM 非対応の実装でも通常のリグ済み
glTF として読める)。R1-4 の検証ハーネスがそのまま `ok: true` を返す。

### 実装時に踏んだ罠

**ノードのワールド位置を「平行移動の累積」で求めてはいけない。**
Blender の glTF エクスポータはボーンをローカルY軸方向へ向けて出すため骨格ノードには
必ず回転が入っており、回転を無視すると前後関係が逆に出る(最初「つま先が +Z 側に
ない」と誤判定した)。TRS を4x4行列で正しく累積したところ、Godot が報告する
スケルトンのボーン位置と**小数3桁まで一致**した(相互検証になっている)。
回帰テストは `test_world_translation_accounts_for_rotation`。

## 15. R3 プレビュー・モーション・ポーズ駆動(2026-07-25)

### 計画からの変更: three-vrm は使わなかった

VRM 出力(§13)と同じ構図。**rig-service の出力は標準スキン付きの正当な glTF**
なので、素の three.js の `GLTFLoader` だけで読み込みもポーズ適用もできる。
three-vrm が足すのは表情・スプリングボーン・MToon・一人称視点といった
**現状出力していない VRM 固有機能**だけだった。

しかも three.js r160 (MIT) は image-3d が既に `web/vendor/` に持っていたため、
**新規ダウンロードゼロ**で実装できた(ファイルをコピーしただけ)。

### 実装

| 対象 | 内容 |
|---|---|
| `web/viewer.js` | `RigViewer` クラス。GLBロード・OrbitControls・`SkeletonHelper` による骨表示・ポーズ適用 |
| `web/index.html` | 3Dプレビュー、ポーズプリセット、ボーン別 XYZ スライダー、骨表示トグル、ポーズ済みGLB保存 |
| `server/pose.py` | ポーズ適用(純Python)。クォータニオン/オイラー角、VRM名でも指定可 |
| `POST /api/rig/jobs/{id}/pose` | ポーズ済み GLB / VRM を返す |

**ポーズはブラウザ内で当てる**。28MBのGLBを操作のたびに往復させないため、
three.js 側でボーンの回転を直接書き換える。サーバのAPIは
「ポーズ済みファイルを書き出す」ときだけ使う。

### 実装時に踏んだ罠

**1. オイラー角「XYZ順」の意味がライブラリごとに違う**

| | 合成順 |
|---|---|
| three.js `new THREE.Euler(x, y, z, "XYZ")` | **Rx·Ry·Rz** |
| Blender `mathutils.Euler((x, y, z), "XYZ")` | **Rz·Ry·Rx**(逆) |

当初サーバをBlender側の順で実装していたため、**2軸以上を同時に回したボーンだけ
静かに5mmズレた**(単軸のボーンは完全一致するので気づきにくい)。
glTF / three.js を基準に統一し、Blenderを使う `tests/pose_preview.py` も
クォータニオンで渡すよう変更。閉じた式で規約を固定する回帰テストを追加した
(`test_quat_from_euler_matches_threejs_xyz_convention`)。

**2. `Box3.setFromObject` はスキンメッシュの行列更新前だと嘘をつく**

シーンに追加した直後(描画1フレーム目の前)はボーンのワールド行列が古く、
実寸 1.61×1.60×1.08m のモデルに対して 1.03×0.82×0.82m の箱が返り、
カメラが寄りすぎて頭が切れた。`updateMatrixWorld(true)` +
`skeleton.update()` + `computeBoundingBox()` を挟んで解決。

**3. hidden な要素の中で WebGL を初期化するとキャンバスが 1x1 になる**

`clientWidth` が 0 のまま `setSize` されるため。`ResizeObserver` で
実表示サイズの変化を拾うようにした。

### 検証結果

**ブラウザ・サーバ・Blender の3面で同じポーズになることを数値で確認した。**
同じポーズを (a) three.js でクライアント適用、(b) `POST .../pose` でサーバ適用
した結果のボーンのワールド座標を比較し、**全ボーンで差 0**
(規約修正前は手が 5mm ズレていた)。Blender の `pose_preview.py` の描画とも
見た目が一致する。

### R3-2 同梱モーションクリップ

外部アセットは持ち込まず**手続き的に自前生成**した(ユーザー判断)。
`server/motions.py` に idle(待機/呼吸) / wave(手を振る) / bow(お辞儀) /
walk(その場歩き) の4クリップ。

**bpy は使わなかった。** クリップの実体はボーン回転のキーフレームの数値で、
Blender の機能を必要としない。rig-service のリグは常に同じ21ボーン・同じ名前
なので、クリップは**どのモデルにも使い回せるモデル非依存のデータ**になる。
純Pythonなら起動1〜2秒もサブプロセスも要らず、テストも速い(22件が0.03秒)。

用途は2つ:

| 用途 | 方法 |
|---|---|
| ブラウザ再生 | `GET /api/motions` でクリップを配り、three.js 側で slerp 補間する |
| Godot等での再生 | `download?motion=walk` で **glTF アニメーションとして焼き込む** |

焼き込みで注意が要るのは、**glTFのアニメーションチャンネルはノードの絶対
ローカル回転を上書きする**こと。クリップはレスト姿勢からの相対回転なので、
焼く際に `R_rest * R_clip` を計算して入れる必要がある。

ループするクリップは先頭と末尾のキーが一致していないと繋ぎ目で跳ねるため、
テストで機械的に検査している(`test_looping_clips_start_and_end_at_same_pose`)。

### 検証結果(R3-2)

- ブラウザ: クリップ選択→再生→シークが動作。walk の1秒ループが実時間通りに進む
- **Godot**: 焼き込んだGLBを取り込むと `AnimationPlayer` にクリップ `walk`(1.0s)が
  現れ、再生すると左手が **0.44m 移動**する(`godot_check` が機械判定)

### 残り

- **VRMA / BVH の読み込み**(R3-3 の一部): 外部モーションファイルの取り込みは未実装。
  同梱クリップと自前ポーズJSONで動かす分には不要なため保留。
